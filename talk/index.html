Part one · The thesis

The comforting message

Software fundamentals matter now more than they actually ever have. Matt Pocock

The fear: AI writes the code, so twenty years of engineering craft is now worth nothing.

The argument: the opposite. AI raises the value of a good codebase and raises the cost of a bad one — because a codebase you cannot safely change is a codebase AI cannot safely accelerate.

The chain

  • AI in a good codebase performs really well
  • So good codebases matter more than ever
  • So software fundamentals matter more than ever

Part one · The failure that started it

The spec-to-code loop degrades

Write a spec, generate code, don't look at the code. Bug? Change the spec, run the "compiler" again.

What actually happens: run one gives code, run two gives worse code, run three gives worse still. Keep going and you have garbage.

This has a name already — software entropy. Every change made while thinking only about that change, and never about the design of the whole system, degrades the system.

Complexity (Ousterhout)

Anything about the structure of a system that makes it hard to understand and modify. A bad codebase is one you cannot change without causing bugs.

The slogan being sold

"Code is cheap." Ignore the code, let it manage itself.

That is vibe coding by another name.

software entropythe tendency of a codebase to drift into disorder as changes pile up, unless someone pushes back complexitynot difficult maths, but anything about a system's structure that makes it hard to understand or change spec-to-coderegenerating the whole codebase from a written specification instead of editing the code vibe codinggenerating code from prompts and shipping it without reading what came out
A Philosophy of Software Design — John Ousterhout · The Pragmatic Programmer — Hunt & Thomas

Part one · Failure mode 1

"The AI didn't build what I wanted"

Diagnosis. No one knows exactly what they want. Talking to the AI is requirements gathering — and you and it do not share the same picture.

The design concept (Frederick Brooks): when two parties design something together, the idea of the thing floats between them. It is not an artifact. You cannot put it in a markdown file. It is the invisible theory of what is being built.

Fix. Reach a shared design concept before producing any plan asset.

The skill, in two lines 
Interview me relentlessly about every
aspect of this plan until we reach a
shared understanding.

Walk down each branch of the design
tree, resolving dependencies between
decisions one by one.

Result: 40, 60, sometimes 100 questions before it is satisfied. The conversation then becomes the PRD or the issue — not the other way round.

Contrast with default plan mode: it is eager to produce an asset and start working. Alignment first is cheaper than rework.

design conceptthe shared mental picture of what is being built; it lives between people, not in a file design treethe branching set of decisions a design implies, where each choice opens or closes later ones requirements gatheringworking out what someone actually needs, as opposed to what they first asked for PRDproduct requirements document — the written statement of what will be built, and why

Part one · Failure mode 2

"The AI is way too verbose"

Diagnosis. You are talking across purposes. This is exactly the old developer-and-domain-expert gap: they use terms you don't hold, you translate them into code neither of you can verify.

Fix — a ubiquitous language (DDD): conversations among developers, expressions in the code, and conversations with domain experts all derive from the same domain model.

In practice, a markdown file of agreed terms — scanned from the codebase, then kept open while planning.

The observed effect
  • Planning quality goes up
  • The model's own thinking traces get shorter — it stops narrating around a concept it now has a word for
  • Implementation lands closer to what was planned
ubiquitous languageone agreed word per concept, used identically in conversation, documents and code domainthe subject the software serves — claims, payments, usage metrics — not the software itself domain expertthe person who knows that subject deeply but does not write the code thinking tracesthe model's visible internal reasoning before it produces an answer
Domain-Driven Design — Eric Evans

Part one · Failure mode 3

"It built the right thing, and it doesn't work"

Obvious layer: feedback loops. Static types. Browser access for front-end work. Automated tests.

The non-obvious part: even with those loops, the model does not use them the way a veteran does. It writes an enormous amount, then thinks "I should probably type-check that."

Outrunning your headlights. The rate of feedback is your speed limit.
Why TDD, specifically

Not because tests are virtuous. Because TDD is a mechanical constraint that forces small steps:

  • Write the test first
  • Make it pass with the smallest change
  • Refactor — and consider the design

The model cannot outrun a loop it has to close on every step.

feedback loopanything that tells you quickly whether the last change was right — types, tests, a browser static typeschecks that catch mismatched data before the code is ever run outrunning your headlightsmoving faster than you can see, so a mistake surfaces long after it was made TDDtest-driven development — failing test first, smallest change to pass it, then improve the design

Part one · Failure mode 4

Testing is hard — because the decisions are entangled

Every test forces coupled choices:

  • How big is the unit under test?
  • What gets mocked?
  • Which behaviours are even worth asserting?

Test a whole application and it is flaky, so you test fewer behaviours. Test this unit and you must mock that one. None of these decisions is independent.

The pivot back to code

Good codebases are testable codebases.

Which closes the loop: better structure → better feedback loops → better feedback to the model → better code out.

Testability is an architectural property, not a testing-discipline property.

unitthe slice of code one test exercises; choosing its size is the first hard decision mocka stand-in for a real dependency so a test can run without it flakya test that passes and fails on identical code, so it stops meaning anything testabilityhow easily a system can be verified from outside — a property of its design, not its tests

Part one · The central structural idea

Deep modules, not shallow ones

Shallow — what AI produces by default

Little functionality, complex interface. Dozens of tiny pieces the model has to walk to understand anything — and it often does not reach the right one in time.

Deep — the same code, bounded

Lots of functionality behind a simple interface. You can look inside; you don't need to.

Who owns what

You design the interfaces carefully. The implementation inside can be delegated.

Why it is testable

The boundary is simple: test at the interface, verify through the interface, done. A codebase that rewards TDD.

Why the model does better

Fewer, clearer things to navigate before it can change anything correctly.

modulea self-contained piece of the system with a boundary drawn around it interfacethe small surface a module exposes — everything a caller has to know about it deep modulea lot of functionality hidden behind a small, simple interface shallow modulelittle functionality behind a comparatively large or fiddly interface

Part one · Failure mode 5

"I can ship more than ever, and my brain can't keep up"

More output means more review, more context, more system held in your head at once. A shallow codebase forces you to hold all of it too — not just the model.

Deep modules give you gray boxes. Design the interface. Understand the purpose. Verify from the outside. Don't read every line inside.

The boundary of that permission is risk — finance, security, safety, anything correctness-critical still gets read. Most modules in most apps do not.

Tip five

Design the interface.
Delegate the implementation.

The consequence for planning

If modules are the unit of delegation, then every plan has to name the modules and interfaces it touches — not just the feature it adds. Module structure becomes part of the ubiquitous language.

gray boxsomething judged by its boundary and behaviour without reading the inside — between a black box (opaque) and a white box (fully inspected) correctness-criticalcode where being wrong is expensive: money, safety, security, compliance

Part one · The close

Invest in the design of the system every day

Spec-to-code does not invest in the design of the system.
It divests from it.

Every regeneration that ignores structure spends the system's remaining changeability.

The division of labour

AI is an excellent tactical programmer — the sergeant on the ground making the change.

Someone has to be operating at the strategic level: architecture, requirements, risk, what "correct" means. That is you, and it needs exactly the fundamentals we have used for twenty years.

divestto run an asset down rather than build it up; here, spending the system's remaining changeability tacticalsolving the change directly in front of you strategicshaping the system so that future changes stay cheap
Kent Beck · "Invest in the design of the system every day."

Part two

What we actually applied

Not "we agree with the talk". A traceable audit of what changed in ghcp-usage-metrics, including the part we got wrong.

The project

Reads local GitHub Copilot logs — VS Code, Copilot CLI, Claude Code — and reports credits, tokens, requests per project, model, agent and skill. Pure stdlib. Ships as a script, a VS Code extension, and a chat skill.

The one rule

Only show what GitHub actually recorded.

No estimation, no interpolation, no back-filling. A gap is reported as a gap. This constraint shapes almost every design decision below.

Why it is a fair test

A measurement tool has nowhere to hide. If the architecture lets a wrong number through, the product is the wrong number.

extractorthe part that reads raw log files and turns them into structured numbers harnessthe tool a request came from — VS Code, the CLI, Claude Code credits / AIUGitHub's own unit of AI usage, taken straight from the log, never calculated by us stdlib onlyuses nothing but the language's built-in libraries — nothing extra to install or trust

Part two · Ubiquitous language

DOMAIN.md — and why it exists

It was not written because DDD recommends it. It was written because of a specific failure:

The failure

The claim "GitHub's per-day telemetry records no model" was written into three files, quoted in the docs, and pinned by a passing test.

It was false. The logs had carried the date and the model on the same event all along — the code was discarding the pairing.

Nothing caught it, because a rule that lives in prose has nothing to fail against.

A slice of the agreed vocabulary

Where code and UI disagree — code says client, the UI says "Harness" — the equivalence is recorded as a decision rather than quietly tolerated.

The principle

A rule that lives only in a comment cannot be violated. It can only be contradicted — silently.

So the register is the ubiquitous language with teeth: it is the shared vocabulary plus the mechanism that makes disagreement fail loudly.

Part two · The honest slide

We were not doing TDD. Here is what it cost.

For most of the project the loop was: build the feature, then wrap tests around what was built. Those tests pass. They also encode whatever the code already does, including its mistakes.

The concrete bill

A false claim — that a model filter could never re-scope headline credits — was documented in three places and pinned by a passing test.

A test written first would have been unpassable. It would have forced the discovery days earlier.

What the test-last loop produces 
write code
observe behaviour
assert the behaviour you observed   ← green, and meaningless
What the test-first loop produces 
assert the behaviour you want
watch it fail — for the predicted reason
smallest change that makes it pass
run everything; a failure elsewhere means
the change is wrong, not the test

That last line is now a written rule in the repo's own instructions file.

test-lastwriting the test after the code, so it records what the code does rather than what it should do pinned by a testa wrong behaviour protected by a passing test, so correcting it looks like breaking something green / reda suite where every test passes / one where something fails

Part two · The payoff

The discovery the false test was hiding

Once the claim was tested instead of asserted, the cause was obvious: the extractor read the timestamp and the model from the same log event, then wrote them into two separate aggregates — discarding the pairing.

# before — the pairing is thrown away
by_day[date]   += usage
by_model[model] += usage

# after — a new dimension keeps it
by_dm[date + SEP + model] += usage

The date × model pairing was in the raw logs the whole time. The limitation was ours, not GitHub's.

The proof, as an invariant

by_dm must decompose on both axes — summed per date it equals by_day; summed per model it equals by_model. Verified against real data, not fixtures.

What the user got

A model filter that re-scopes everything — credits, requests, projects, days — instead of a checkbox that dimmed one row and changed nothing.

Cost of the wrong dimension: the claim was written three times, believed for weeks, and defended by CI.

aggregatea running total kept while reading the logs the pairingthe fact that two values arrived on the same log event and therefore belong together CIcontinuous integration — the automated test run that guards every change

Part two · Deep modules

Two files were the system. Now they are the seam.

Before 
usage.py             1001 lines
dashboard_template.py 2249 lines

Everything: paths, parsing, aggregation, diagnostics, HTML, CSS and JS. One render() of ~155 lines did filtering, aggregation and painting.

After 
usage.py              216   entry + paths
build_dashboard.py     50   assembler
ghcp/        12 modules     38–337 lines
web/js/      12 modules     46–317 lines

render() split into computeScope → aggregate → painters.

Deep, not merely split

ghcp/scan/vscode.py is the biggest module at 337 lines — deliberately. It hides debug logs, chat sessions, subagent child logs and skill attribution behind one call.

The safety method

Golden masters first: a hash of the assembled HTML and a full snapshot of the output. Proven to catch a one-character change. Then slice at exact boundaries and assert the parts rejoin byte-identically before deleting the original.

Interface designed, implementation delegated

Scanners take explicit paths, so they are independently testable. usage.py keeps zero-argument wrappers that read module globals at call time, so the test injection seam never moved.

assemblercode that stitches separate source files together into one output file byte-identicalliterally the same file, not merely equivalent-looking injection seamthe one place a test can point the code at a fake filesystem instead of the real one zero-argument wrappera thin function that reads its settings at call time, so a test can change them late

Part two · Entropy control

Making decay fail a test instead of a user

The tool ships from one source but runs from four places — repo, committed skill bundle, the global agent skill, and the packaged extension. None of them notice when they fall behind. A stale copy just quietly reports different numbers.

The fix

test_bundle_sync.py fails when any copy drifts. A forgotten sync shows up as a red test, not as wrong numbers weeks later.

Paired with an instructions file scoped to exactly the files that trigger it — so the rule reaches whoever edits them, human or agent.

Two guards that earned their place immediately

One home for the placeholder

A magic string was hardcoded at five sites. A guard test asserts the literal appears in exactly one module — and on its first run it found a sixth occurrence that had been missed.

Delete the fallback, let it raise

An unknown-model placeholder was probed against the live snapshot: zero hits across 51 projects and 14,119 requests. It had never once fired. So it was deleted rather than dignified with a constant — a missing model now raises and lands in Diagnostics naming the file.

magic stringa bare literal value repeated across the code, with no name and no single home fallbacka default used when the expected value is missing — convenient, and very good at hiding real problems raisestop and report the error instead of quietly substituting something plausible guard testa test whose only job is to stop a known bad habit reappearing

Part two · What generalises

Lessons the talk did not give us — the project did

01

A rule in prose has nothing to fail against

The lesson from the contradictory comment is not "update your comments". It is that prose is the wrong home for a rule. Move it somewhere it can go red.

02

Red for the wrong reason is not red

A fixture writing to a key nothing reads fails with the right message and the wrong cause. Read the failure before writing the fix.

03

Fixtures must be faithful, not convenient

A filter looked complete against invented data where the awkward rows sat alone. In real logs they sit beside normal usage — and a default filter was deleting the invented project before the assertion ran.

04

Never derive scope from DOM the same render is about to rewrite

Reading checkbox state back from the page made the filter lag by one render. State lives in the state object; the DOM is an output.

05

Pass now as an argument

The forecast takes the current time as a parameter instead of reading the clock. Month-end and leap-year arithmetic became deterministic and testable. Do this for anything time-dependent.

06

A control whose only effect is on another tab reads as broken

The model filter worked perfectly and was reported as a bug, because every surface it changed was somewhere else. Give feedback at the point of interaction.

DOMthe live structure of the page as the browser holds it renderone pass of redrawing the page from the current state scopethe subset of data currently selected for display deterministicthe same inputs always give the same result — which is what makes it testable

Part two · Honest accounting

What it cost, what it bought

The cost

  • Two large files became 26 modules across two languages — more files to navigate
  • 242 tests to keep green on every change
  • Four copies to keep synchronised, plus the machinery that checks them
  • A domain document and an invariant register that must be updated with the code
  • Output grew from 130 KB to 186 KB to carry the new dimension

None of this was free, and none of it was refactoring for its own sake. Each piece was added after something specific went wrong.

What it bought

  • A whole capability that had been declared impossible three times — found by testing the claim instead of repeating it
  • Refactors that are provably behaviour-preserving, byte for byte
  • A rename or a stale bundle fails CI instead of silently changing someone's numbers
  • Sizeable changes delegated to the model inside modules, verified at the boundary
  • Documentation that cannot drift from the code without failing a test
The measurable state

51 projects · 451 sessions · 14,353 requests · 202,804.84 credits · 90 active days — every figure traceable to a recorded log event.

behaviour-preservingrestructured code that provably does exactly what it did before greenevery test passing — the state a change has to leave the repo in

Close

The takeaway

Code is not cheap. AI is a superb tactical programmer.
The strategic layer is still yours — and it runs on fundamentals we already had.
Say what the words mean

Ubiquitous language, agreed once, used in requirements, code and conversation alike.

Make every rule fail-able

If it matters, it has a test. If it has no test, say so out loud.

Keep the loop short

Test first. Smallest change. The feedback rate is the speed limit.

Own the interfaces

Design them yourself. Delegate what sits behind them. Verify from outside.
